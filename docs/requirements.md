# 요구사항 명세서

> 프로젝트: 콘서트 티켓팅 Backend Starter-Kit
> 참고 도메인: NOL 유니버스, 인터파크 티켓 유사 서비스
> 관련 문서: [아키텍처 문서](./architecture.md) · [ERD](./erd.md) · [API 명세서](./api-spec.md)

## 1. 개요

### 1.1 목적
실제 대규모 콘서트 티켓팅 서비스(NOL 유니버스 등)에서 발생하는 핵심 기술 문제 — **오픈런 트래픽 폭주**, **좌석 동시 선점 충돌**, **예약-결제 정합성** — 를 재현하고 학습할 수 있는 Spring Boot 기반 backend starter-kit을 구축한다.

### 1.2 범위
- 포함: 콘서트/좌석 조회, 대기열 진입/승급, 좌석 선점(2가지 동시성 전략), Mock 결제, 티켓 발급, 인증/인가
- 제외(향후 확장 포인트로만 명시): 실제 PG 연동, 환불/취소 정책의 상세 구현, 알림(이메일/푸시), 관리자 대시보드 UI, 다국어 지원

### 1.3 용어
자세한 용어 정의는 [용어집](./glossary.md) 참고.

## 2. 이해관계자 (Stakeholder)

| 역할 | 설명 |
|---|---|
| 일반 사용자 (User) | 콘서트를 조회하고 좌석을 예매하는 최종 사용자 |
| 관리자 (Admin) | 콘서트/좌석 등급/좌석을 등록·관리하는 운영자 |
| 개발자 (starter-kit 사용자) | 이 코드베이스를 학습·재사용하여 자신의 서비스를 구축하는 개발자 |

## 3. 기능 요구사항 (Functional Requirements)

| ID | 요구사항 | 우선순위 | 관련 유즈케이스 |
|---|---|---|---|
| FR-01 | 사용자는 이메일/비밀번호로 회원가입할 수 있다 | High | UC-01 |
| FR-02 | 사용자는 로그인하여 인증 토큰(세션)을 발급받을 수 있다 | High | UC-02 |
| FR-03 | 사용자는 콘서트 목록을 조회할 수 있다 (상태별 필터링 포함) | High | UC-03 |
| FR-04 | 사용자는 콘서트 상세 정보와 좌석 등급별 가격을 조회할 수 있다 | High | UC-03 |
| FR-05 | 사용자는 콘서트별 좌석 배치도(좌석맵)와 각 좌석의 상태(AVAILABLE/HELD/RESERVED)를 조회할 수 있다 | High | UC-04 |
| FR-06 | 시스템은 예매 오픈 시각 이전에는 좌석 선점/예약 API 요청을 거부해야 한다 | High | UC-04 |
| FR-07 | 시스템은 대기열 기능이 활성화된 콘서트에 대해, 사용자가 대기열에 진입하고 순번을 확인할 수 있게 해야 한다 | High | UC-05 |
| FR-08 | 시스템은 대기열 순번에 도달한 사용자에게 시간 제한이 있는 입장권(토큰)을 발급해야 한다 | High | UC-05 |
| FR-09 | 시스템은 유효한 입장권이 없는 사용자의 예약 API 호출을 거부해야 한다 (대기열 활성화 시) | High | UC-05 |
| FR-10 | 사용자는 좌석을 선점(HOLD)하여 임시로 예약을 생성할 수 있다 | High | UC-06 |
| FR-11 | 시스템은 동일 좌석에 대한 동시 선점 요청 중 정확히 하나만 성공시켜야 한다 | Critical | UC-06 |
| FR-12 | 시스템은 좌석 선점 시 Redis 분산락 방식과 DB 비관적 락 방식 두 가지를 모두 제공해야 한다 | Critical | UC-06 |
| FR-13 | 시스템은 좌석 선점 후 일정 시간(기본 5분) 내 결제가 완료되지 않으면 예약을 자동 만료시키고 좌석을 반환해야 한다 | Critical | UC-09 |
| FR-14 | 사용자는 선점한 좌석에 대해 Mock 결제를 요청할 수 있다 | High | UC-07 |
| FR-15 | 시스템은 결제 성공 시 예약 확정, 좌석 상태 변경, 티켓 발급을 정합성 있게 처리해야 한다 | Critical | UC-07 |
| FR-16 | 시스템은 결제 실패/타임아웃 시 좌석을 즉시 반환하여 재선점 가능하게 해야 한다 | High | UC-08 |
| FR-17 | 사용자는 자신의 예약 내역과 발급된 티켓을 조회할 수 있다 | Medium | UC-10 |
| FR-18 | 사용자는 공연 D-1 이전까지 예약을 취소할 수 있다 | Medium | UC-11 |
| FR-19 | 관리자는 콘서트, 좌석 등급, 좌석을 등록/수정할 수 있다 | Medium | UC-12 |
| FR-20 | 시스템은 콘서트의 전체 좌석이 모두 예약 완료되면 콘서트 상태를 SOLD_OUT으로 자동 전환해야 한다 | Medium | UC-06 |

### 3.1 우선순위 정의
- **Critical**: 도메인 핵심 학습 목표(동시성 제어, 정합성). 미구현 시 starter-kit의 존재 의미가 없음
- **High**: 핵심 예약 플로우의 필수 기능
- **Medium**: 완성도를 높이는 부가 기능, MVP 이후 구현 가능

## 4. 비기능 요구사항 (Non-Functional Requirements)

| ID | 카테고리 | 요구사항 |
|---|---|---|
| NFR-01 | 동시성 | 동일 좌석에 대한 100건 이상의 동시 요청 시에도 정확히 1건만 성공해야 한다 (정합성 최우선, 성능은 2차) |
| NFR-02 | 성능 | 좌석맵 조회 API는 평상시 200ms 이내 응답을 목표로 한다 (캐시 활용) |
| NFR-03 | 확장성 | 대기열 시스템은 애플리케이션 서버 다중화(수평 확장) 환경에서도 정상 동작해야 한다 (상태를 Redis에 위임) |
| NFR-04 | 테스트 가능성 | 모든 핵심 비즈니스 로직(좌석 선점, 대기열, 결제)은 TestContainers 기반 통합테스트로 검증 가능해야 한다 |
| NFR-05 | 이식성 | 로컬 개발 환경은 Docker Compose로 MySQL/Redis를 기동하여 실제 서비스와 동일한 조건에서 개발할 수 있어야 한다 |
| NFR-06 | 보안 | 비밀번호는 평문 저장 금지, Spring Security 기반 암호화 저장 및 인증을 적용한다 |
| NFR-07 | 관측성 | 두 가지 동시성 전략(Redis/DB 락)의 처리 결과를 비교할 수 있도록 API 응답 또는 로그에 처리 방식이 식별 가능해야 한다 |
| NFR-08 | 문서화 | 모든 API는 SpringDoc OpenAPI(Swagger UI)를 통해 자동 문서화되어야 한다 |
| NFR-09 | CI | 모든 PR/push에 대해 빌드와 테스트가 자동 실행되어야 한다 |

## 5. 제약사항 (Constraints)

| 항목 | 내용 |
|---|---|
| 기술 스택 | Spring Boot 4.0.7, Java 17, MySQL, Redis, Spring Security, JPA — 변경 불가(기확정) |
| 동시성 라이브러리 | Redis 분산락은 Redisson 사용 (`redisson-spring-boot-starter` 추가 필요) |
| 모듈 구조 | 단일 Gradle 모듈, 도메인 기반 패키지 구조(DDD 스타일) |
| 결제 | 실제 PG 연동 없이 Mock 결제로 구현 (100% 성공/실패를 임의 제어 가능하게 설계) |
| 배포 대상 | 미정 — CI 파이프라인은 빌드+테스트까지만 포함, 배포 단계 제외 |

## 6. 가정 (Assumptions)

- 한 콘서트는 여러 회차를 갖지 않는다 (1 Concert = 1 공연 일시). 회차 개념이 필요하면 향후 `ConcertSchedule` 엔티티로 확장
- 좌석은 사전에 관리자가 모두 생성해두고, 사용자가 신규 좌석을 만들지 않는다
- 결제 수단은 Mock으로 단순화하며, 실제 카드/간편결제 연동 로직은 범위 밖이다
- 대기열은 설정(`app.queue.enabled`)으로 켜고 끌 수 있어, 학습자가 대기열 없이 핵심 예약 플로우만 테스트할 수도 있다

## 7. 추적성 (Traceability)

각 기능 요구사항(FR)은 [유즈케이스 문서](./use-cases.md)의 UC 번호와 매핑되며, UC는 다시 [API 명세서](./api-spec.md)의 엔드포인트 및 [테스트 시나리오](./test-scenarios.md)의 테스트 케이스와 연결된다.
